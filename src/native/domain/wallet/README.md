# Wallet Domain

The platform layer under the verifiable-credential wallet (decision records ADR-0009, ADR-0005,
ADR-0014 §2 in the parent repository; app-side decisions in `docs/adr/0003-wallet-platform-layer.md`).
Protocol and cryptography live in `@identra/sdk-app` / `@identra/sdk-core`; this folder only wires them.

## Files

- `walletContainer.ts`: pure `createWallet(deps)`: key store, vault (catalogue-syncing), the SDK wallet object (`offers`, `credentials`) with the pinned roots, the trust-list URL and the diploma as the only supported type, start-up state, restore list, issuer-name cache. Tested in Node.
- `walletRuntime.ts`: the memoised instance on the real Expo modules (`getWallet` / `getWalletApi`), the pending scanned offer, and `handOffWalletRequest`, the single entry from the QR scanner.
- `pinnedRoots.ts`: the Identra Root CA(s), generated by `scripts/generate-pinned-roots.mjs` from the website's `root-ca.pem` (array: a second root during a rollover).
- `walletMessages.ts`: every SDK/wallet code → one plain sentence + the action a person can take (`Record`s over the SDK unions: a new code does not compile until it has a sentence).
- `walletViews.ts`, `walletFlows.ts`: what the screens show and the receive / detail / restore state machines (pure reducers).
- `presentationFlow.ts`: sharing (OpenID4VP): the consent state machine (untrusted double confirmation, single submit, countdown expired from resolve time, revoked / suspended / invalid / expired block, document chooser), required / optional / withheld fields and every option of the claim sets, the verifier's purpose (trusted only), the activity record (field names, never values; outcome success / failed / uncertain), and `createPresentationActions`: the consent screen's "Chia sẻ" (reducer selection, `allowUntrusted` only after the second confirmation, one call at a time) and leave (local decline).
- `walletFlows.ts` also holds the receive screen's `runAccept` (PIN only on the PIN step) and `abandonOffer` (discard on leave). Receive failures route by `retryable` and `codeRedeemed` (ADR 0003 "Review fixes").
- `src/native/data/wallet/catalogueFile.ts`: the backup catalogue file writer (write, verify, swap through `.prev`; see ADR 0003).
- `credentialPresentation.ts`: `vct` → document name, diploma claim labels and order, date format, status → app status. Returns i18n keys.
- `src/native/dev/walletHarness.ts`: DEV ONLY scripted wallet for web screenshots (`EXPO_PUBLIC_WALLET_HARNESS=1`); never in a normal bundle.
- Adapters: `src/native/data/wallet/*` (random, HTTP, SecureStore, SQLite, AsyncStorage seen-store).
- Runtime globals and self-check: `src/native/platform/*`, imported first by `index.ts`.

## Invariants

- One wallet per app process; created on first use, never at import.
- Wallet keys: SecureStore, biometrics on every read, `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, service `identra.wallet.keys`. The vault data key: no biometrics, `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, service `identra.wallet.vault`.
- `SecretStorage.get` resolves `null` only for "not found". Cancelled prompt, locked device, invalidated key and any other failure reject with `SecretStorageError` (codes `CANCELLED`, `LOCKED`, `KEY_INVALIDATED`, `UNAVAILABLE`). `KEY_INVALIDATED` = biometrics changed: that credential must be requested again.
- SQLite file `identra-wallet.db`, table from the SDK's `CREDENTIALS_TABLE_DDL`, version in `PRAGMA user_version`, bound parameters only, one statement at a time. The repository lists its columns explicitly: a new SDK column needs a migration here, or its value is dropped (for `issuer_did` that would make DID-path rows `UNDECRYPTABLE`).
- The backup catalogue file `identra-backup-catalogue.json` lists document type and issuer only. It keeps documents that a restored phone still has to request again: a save adds, a removal drops only what no row holds, `forgetDocument` drops on request.
- Rows without the data key (`restored-device`) are never deleted until the user confirms (`acknowledgeNewDevice`).
- Errors carry codes only: no key, data key, compact credential, claim value, URL or native message.
- HTTP: https only (plus the mapped development origin), no redirects, no cookies, 10 s default timeout, 256 KB body cap.

## DID trust path (ADR-0020)

Beside the X.509 path, an issuer can be a `did:certnet` DID checked through CertNet (key from the
gateway's DID document, recognition from its trust registry). The SDK does every check; the app
configures it, stores one column and says on screen which path was used.

- **Configuration** (public, inlined at build time, see `.env.example`): `EXPO_PUBLIC_CERTNET_GATEWAY_URL`
  (an `https://` origin, optionally with a path; no query, fragment or userinfo) and
  `EXPO_PUBLIC_CERTNET_NETWORK` (`local`, `testnet` or `mainnet`). Both or neither. Neither: the DID
  path is off and the wallet behaves exactly as before (a DID issuer's offer is refused at resolve
  with `TRUST_PATH_UNSUPPORTED`, before the PIN). `certNetConfigOf` validates them: one without the other, an
  unknown network, `local` in a release build (anyone can write the local trust registry) or a URL
  the SDK refuses is a `WalletConfigError`; a development build stops on it, a release build runs
  with the DID path off rather than lose the X.509 wallet. The gateway is trusted configuration
  (its answers are unsigned, ADR-0020 §9).
- **Network**: `createGatewayHttpFetch` (data/wallet/httpFetch.ts) is the wallet's own adapter
  (https, no redirect, no cookies, timeout and size cap) restricted to the gateway's origin; the
  resolver and the trust registry are its only users. There is no development mapping to an http
  gateway: test against an https gateway or the SDK's fake gateway (tests).
- **Migration**: schema version 3 adds the nullable `issuer_did` in place (`ALTER TABLE ... ADD
  COLUMN`, one transaction with the version stamp); a version 1 table is rebuilt straight to 3. Rows
  from before have NULL there and read and open as X.509. The repository writes and reads the
  column; the SDK binds it to the ciphertext.
- **What the screens say** (`walletViews.ts`: `issuerViewOf`, `issuerText`, `issuerIdText`, `trustPathKey`,
  `statusSentenceKeys`): X.509 keeps the trust-list name and adds "Nơi cấp nhận diện qua chứng nhận số";
  the DID path never shows a name (not the issuer's own, not its web origin, not `knownIssuers`,
  not the name cache, all keyed by issuer URL, which both paths share; `withIssuerNames` in the
  container): "Mã nơi cấp <id>" and "Nơi cấp tra cứu qua CertNet" ("(mạng thử nghiệm)" for `local` /
  `testnet`). The path line names how the issuer is looked up, never the outcome: only the status pill
  says that. **Identifier rule** (`issuerIdText`, one place): the registrant chooses its identifier, so
  a shortened one can be imitated. Complete (wrapped, never shortened) wherever a person decides or
  relies on who the issuer is: the offer, the received screen, the share consent, the detail. Dense
  surfaces (list card, wallet home): whole up to 41 characters, beyond that the first 20 and last 20
  around "…", never clipped; the card opens the detail, which shows it whole. The detail screen has
  "Cách xác minh nơi cấp": what CertNet is, why there is no name, the full identifier (selectable,
  to compare with the issuer's own) and a test-network note.
- **States**: valid; not checked yet because CertNet did not answer (status `unknown`, the detail
  says it was CertNet, "Kiểm tra lại" retries); issuer no longer recognised (`invalid`, "Nơi cấp
  hiện không được công nhận qua CertNet…"); issuer DID not resolvable at receipt (SDK
  `NETWORK_ERROR` with a `did_resolution` `DID_RESOLUTION_UNAVAILABLE` check, read as
  `DID_RESOLUTION_UNAVAILABLE`: "Thử lại" without the PIN and without a fingerprint prompt, nothing
  saved until it passes; such a retry does not open the credential access gate for two minutes,
  since no biometric prompt happened). Messages: check `did_resolution`, code
  `DID_RESOLUTION_UNAVAILABLE`, and DID-path wording of `ISSUER_NOT_TRUSTED` /
  `TRUST_LIST_UNAVAILABLE` (CertNet, not Identra's list), chosen from the SDK's checks.
- **DID path off** (no CertNet configuration): a DID issuer's offer is refused at resolve with the
  SDK's `TRUST_PATH_UNSUPPORTED` (`OFFER_INVALID` again means only "not a valid offer"): "Ví chưa
  nhận được giấy tờ này", only what the issuer itself says (its documents are checked through CertNet), no word on the QR code, action `scan-again` (another code, never a retry
  of this one). The receive screen of a DID issuer (`ResolvedOffer.issuerDid`, declared and not yet
  verified) shows no name, not even the self-declared one: the web address, "Mã nơi cấp <complete id>"
  and "will be checked through CertNet when you receive it", with "(mạng thử nghiệm)" for a `local` /
  `testnet` identifier, since the identifier shown lacks the network (`offerView`: `issuerName` null,
  `issuerId`, `issuerTestNetwork`). A stored DID credential re-checked in such a build is `unknown`, and
  `statusSentenceKeys` reads the SDK's `did_resolution` / `DID_RESOLUTION_FAILED` on an `unknown` DID
  document as `wallet.didPath.unsupported` ("this version of the app cannot check this document"),
  never "CertNet did not answer" (CertNet was not asked). With CertNet configured that same failure
  is `invalid`. Before any re-check (no checks in hand) an `unknown` DID document says CertNet or the
  issuer did not answer the last check (`wallet.didPath.notCheckedYet`), never "could not reach the issuer". The backup catalogue keeps the issuer
  URL only, so the restore list names a DID issuer by URL (host or `knownIssuers`), as before.

- **Sharing when the requester could not reach CertNet** (`presentationFlow.ts`): the SDK's
  `DID_RESOLUTION_UNAVAILABLE` with `delivered: true` means the requester RECEIVED the document and
  concluded nothing. The history gets one entry ("Đã gửi …, chưa có kết quả", status `pending`); the
  consent screen is locked to that document and claim set (`ConsentState.delivered`): "Gửi lại" (same
  selection) or "Dừng", nothing that changes the selection. A later success replaces that entry (same
  id: what was shared counts once); anything else (the request closed, the SDK's last allowed send
  answered `VERIFIER_ERROR`, a lost connection, stopping) leaves it as "sent, no result" and ends the
  flow with "Yêu cầu không còn dùng được" (never "nothing was sent"); a cancelled prompt returns to the
  locked screen. The sentence says why only as the requester's word ("Họ cho biết…"): the wallet cannot
  know whether they really could not reach CertNet.
- **The lock outlives the screen** (re-review N1): the pin belongs to the request (the QR), not to the
  mounted screen. Leaving the screen (background and the access gate, back, "Dừng") declines the resolved
  object only; the same QR resolved again (a remount, a second scan, a retried "check later") comes back
  with the SDK's `pinned` and opens directly on the locked screen (same wording, "Gửi lại" / "Dừng",
  an untrusted requester counted as confirmed, as on the screen that sent it). The history entry is found
  again by `requestRef` (the QR text the request came from, i.e. verifier `client_id` + `request_uri`:
  what the SDK keys its pin by), status `pending`: every later send updates that entry (`sends`,
  "Đã gửi N lần" when more than once; a send that may have arrived counts too), so there is one entry
  per request. `REQUEST_INVALID` at resolve for a QR with such an entry (its sends are used up) is
  "Yêu cầu không còn dùng được" with "what was sent stays sent", not "this code is not valid"; without
  the entry (history off or cleared) the app cannot tell and says the generic sentence.
- **Across an app restart** the SDK's pin is gone (memory only). The history entry is enough to restore it,
  so the app does: within `lockedUntil` (600 s from the first delivery, never extended), the same QR opens
  locked to that document and the claim set with exactly those field names, keeps the count (the
  larger of the SDK's and the entry's) and closes the request at `MAX_PRESENTATION_SENDS` in all.
  Limits: it needs the sharing history (setting on, entry not deleted); after the 600 s the QR is an
  ordinary request again, as with the SDK's own pin; if the requester no longer offers exactly those
  fields, the request is closed, never opened unlocked.
- **Network**: `dpki.network` is the configured network: an offer declaring an identifier of another
  CertNet network is `TRUST_PATH_UNSUPPORTED` at resolve, before the PIN ("Ví chưa nhận được giấy tờ này").
- **CertNet wording only on the DID path**: `wallet.errors.DID_RESOLUTION_*` are neutral; the CertNet
  sentences (`wallet.didPath.*`) are picked only when the SDK's checks are of the DID path.

## Screens (src/native/screens/identity)

- Receive (`/receive-credential`, from the scanner only: the app has no `openid-credential-offer` URL scheme, and adding one is a native change).
- List (`/credentials`) and detail (`/credentials/[id]`, behind `CredentialAccessGate`) read the vault only; demo credentials never appear there.
- Restore (`/wallet-restore`, also from Settings → Backup).
- Share (`/present-credential`, from the scanner's `presentation-request` only, behind `CredentialAccessGate` like the detail). There is no holder-shown sharing QR: a document is shared only by scanning the verifier's code. Leaving the screen declines locally; values are masked until revealed except the one-line summary of field names, and masked again whenever the app is inactive; the app shell's privacy cover hides the screen in the app switcher (best effort, see the device checklist).
- The PIN stays in the receive screen's component state; it is cleared after a wrong attempt and on unmount.
